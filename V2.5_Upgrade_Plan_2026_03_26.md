### 2.2 Root Cause Analysis

**Why is identity name mention only 17%?**
- The 72 identity anchor examples in training data say "NexiFuse" but are overwhelmed by 40,947 other examples that don't
- The model learned the healthcare domain identity but not the product name
- **Root cause:** Identity anchors are <0.2% of training data:too sparse

**Why is math accuracy 50%?**
- DeepSeek-R1-Distill-8B has strong reasoning but the 8B parameter count limits multi-step calculation
- The base model was trained for code generation, not arithmetic
- Our training data has math examples but with insufficient step-by-step verification
- **Root cause:** Base model limitation + insufficient verified math data

**Why are debugging responses short (6%)?**
- Multi-turn debugging had only 1,599 training examples:smallest category
- Many examples were single-turn Q&A, not deep diagnostic workflows
- The model defaults to brief responses when uncertain
- **Root cause:** Insufficient debugging training data with multi-step solutions

**Why do Mirth responses reference non-existent libraries?**
- The model confabulates Java class names that look plausible but don't exist
- Training data from synthetic generation sometimes includes hallucinated imports
- No grounding mechanism validates API references against real documentation
- **Root cause:** No verifiable reward signal for API correctness (GRPO would fix this)

### 3.3 Math Fix:Detailed Plan

**Why math is hard for 8B models:**
- 8B parameters limits working memory for multi-step calculation
- Q4_K_M quantization further reduces numerical precision
- The model learned to *explain* math but not always *compute* correctly

**V2.5 approach:chain-of-thought math training:**

1. Generate 2,000 math examples using llama3:70b (better at math)
2. **Verify every answer programmatically**:run Python `eval()` on the final answer
3. Only keep examples where the chain-of-thought reaches the correct answer
4. Include healthcare-contextualized math:
   - Throughput calculations (messages/sec, latency percentiles)
   - Storage sizing (GB/year for HL7 archives)
   - Uptime/SLA calculations (99.9% = 8.76 hrs/year downtime)
   - FHIR Bundle size estimation
   - Interface engine capacity planning

**Example of verified training data:**
```json
{
  "instruction": "A hospital processes 2,500 ADT messages per hour. Each message averages 3.2 KB. How much storage is needed for 30 days of raw message archival?",
  "output": "Let me calculate step by step:\n\n1. Messages per day: 2,500 × 24 = 60,000\n2. Messages per 30 days: 60,000 × 30 = 1,800,000\n3. Storage: 1,800,000 × 3.2 KB = 5,760,000 KB\n4. Convert: 5,760,000 KB ÷ 1,024 = 5,625 MB ÷ 1,024 = **5.49 GB**\n\nYou need approximately **5.5 GB** of raw storage for 30 days."
}
```

**Expected result:** 50% → >85% accuracy on complex math

## 4. Training Strategy: SFT + GRPO + SimPO

### 4.1 Why GRPO is Critical for V2.5

GRPO (Group Relative Policy Optimization) uses **verifiable rewards**:our existing validators score each response, and the model learns to produce higher-scoring outputs.

**What GRPO fixes that more data cannot:**

| Problem | Why Data Alone Can't Fix | How GRPO Fixes |
|---------|--------------------------|----------------|
| Hallucinated Mirth libraries | Model needs to learn "don't invent APIs" | Validator scores real APIs higher → model avoids fake ones |
| Inconsistent error handling | Model has both good and bad examples | Reward function scores try/catch code higher |
| Short debugging responses | Model doesn't know "longer is better here" | Reward function scores detailed responses higher |
| Invalid HL7 structure | Model generates plausible but invalid HL7 | HL7 validator gives 0 for invalid → model learns structure |

### 4.2 GRPO Implementation on 8x L4 (with CPU Offloading)

V2 GRPO failed because 8B model + 5 completions per prompt = OOM on a single 22 GB L4.

**V2.5 solution:3 strategies combined:**

**Strategy A: Reduce generations (5 → 2)**
- GRPO with 2 completions per prompt instead of 5
- Reduces peak VRAM from ~25 GB to ~12 GB per GPU
- Still effective:research shows 2 generations captures 80% of GRPO benefit

**Strategy B: CPU offloading via DeepSpeed ZeRO-3**
- Offload optimizer states + gradients to 425 GB system RAM
- Only keep activations and forward/backward pass on GPU
- Unsloth supports this via `device_map="auto"`

**Strategy C: Single GPU with gradient checkpointing**
- Use 1 L4 (22 GB) with aggressive gradient checkpointing
- `max_seq_length=1024` during GRPO (shorter sequences = less VRAM)
- Batch size 1 with gradient accumulation of 8

```
Hardware: GCP VM:8x NVIDIA L4 (22 GB each) + 425 GB system RAM
Model:    DeepSeek-R1-Distill-8B (4-bit NF4) = ~5 GB
2 completions × 1024 tokens = ~7 GB
Gradient checkpointing + optimizer = ~8 GB
Total:    ~20 GB:fits in single L4 (22 GB)
```

**Fallback if all strategies OOM:** Skip GRPO entirely, rely on SimPO only (which uses pre-computed pairs and needs no generation during training:guaranteed to fit).

**Reward function (already implemented in `training_pipeline.py`):**

| Validator | Score | What It Checks |
|-----------|-------|----------------|
| JavaScript syntax | +0.25 | Balanced brackets, valid syntax |
| XML well-formedness | +0.25 | Parseable XML structure |
| HL7 v2 structure | +0.25 | Valid segments, required fields |
| FHIR R4 validity | +0.25 | Valid resourceType, required elements |
| Security scan clean | Bonus +0.10 | No hardcoded secrets, SQL injection |
| Response length | Bonus +0.10 | >500 chars for code prompts |
| **Max score** | **1.20** | |

### 4.3 SimPO Preference Alignment

SimPO (Simple Preference Optimization) improves DPO by not requiring a reference model:6.4 points better on benchmarks.

**How we generate preference pairs:**
1. During new data generation, generate 5 completions per prompt
2. Score each with our validator reward function
3. Keep best (chosen) and worst (rejected) as a pair
4. Target: 3,000 preference pairs

**What SimPO teaches:**
- "This Mirth transformer with error handling is better than this one without"
- "This HL7 message with all required segments is better than this incomplete one"
- "This detailed debugging response is better than this 1-liner"

## 7. GRPO/SimPO Setup on 8x L4

### 7.1 Hardware Reality

```
Available:  8x NVIDIA L4 (22 GB each) = 176 GB total VRAM
            425 GB system RAM (Intel Xeon 48-core)
            3.9 TB SSD

Constraint: V2 GRPO OOM'd with 5 generations on single L4 (22 GB)
            8B model (4-bit) = ~5 GB + 5 completions = ~25 GB > 22 GB
```

### 7.2 GRPO:Fit Strategy

**Option A (Primary): Single L4, 2 generations, short sequences**

```bash
CUDA_VISIBLE_DEVICES=0 \
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True \
python -m nexifuse train-grpo \
  --adapter-path nexifuse_model_adapter \
  --data data/validated/passed.jsonl \
  --num-generations 2 \
  --max-seq-length 1024 \
  --batch-size 1 \
  --gradient-accumulation 8 \
  --gradient-checkpointing \
  --max-steps 500 \
  --learning-rate 5e-6 \
  --output outputs/grpo_adapter
```

Memory budget:
| Component | VRAM | Notes |
|-----------|------|-------|
| Base model (4-bit NF4) | 5 GB | Frozen weights |
| LoRA adapters | 500 MB | Trainable parameters |
| 2 completions × 1024 tokens | 7 GB | Reduced from 5×2048 |
| KV cache + activations | 4 GB | With gradient checkpointing |
| Optimizer (AdamW states) | 3 GB | LoRA params only |
| **Total** | **~20 GB** | **Fits in 22 GB L4** |

**Option B (Fallback): CPU offloading via DeepSpeed ZeRO-Offload**

If Option A still OOM's, offload optimizer to 425 GB system RAM:

```bash
CUDA_VISIBLE_DEVICES=0 \
python -m nexifuse train-grpo \
  --adapter-path nexifuse_model_adapter \
  --data data/validated/passed.jsonl \
  --num-generations 2 \
  --max-seq-length 1024 \
  --cpu-offload \
  --max-steps 500 \
  --output outputs/grpo_adapter
```

This moves ~3 GB optimizer states to RAM, freeing GPU for forward/backward passes.
Trade-off: ~2x slower (CPU↔GPU data transfer) but guaranteed to fit.

**Option C (Last resort): Skip GRPO, SimPO only**

SimPO uses pre-computed preference pairs:no generation during training. Guaranteed to fit on single L4 since it's essentially the same memory footprint as SFT.

### 7.3 SimPO Training Command

SimPO is safe:no generation, same memory as SFT:

```bash
CUDA_VISIBLE_DEVICES=0 \
python -m nexifuse train-simpo \
  --adapter-path outputs/grpo_adapter \
  --preference-data data/simpo/pairs.jsonl \
  --max-steps 300 \
  --learning-rate 1e-6 \
  --gamma 0.5 \
  --output outputs/simpo_adapter
```

Memory budget:
| Component | VRAM | Notes |
|-----------|------|-------|
| Base model (4-bit NF4) | 5 GB | Same as SFT |
| LoRA adapters | 500 MB | Same as SFT |
| Forward pass (chosen + rejected) | 8 GB | 2 sequences per step |
| Optimizer | 3 GB | LoRA params only |
| **Total** | **~17 GB** | **Fits easily in 22 GB L4** |

## 9. Risk Mitigation

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|------------|
| **GRPO OOM on L4** | Medium | High | 3-level fallback: (A) 2 gens + 1024 seq + grad ckpt, (B) CPU offload, (C) skip GRPO, SimPO only |
| **Catastrophic forgetting** | Medium | High | Mix 30% V2 data into V2.5 training. Monitor V2 benchmark scores continuously. |
| **GPU contention (training vs generation)** | Low | Low | Schedule generation on GPUs 1-7 while GRPO uses GPU 0. Never overlap SFT DDP with GRPO. |
| **Identity fix doesn't reach 90%** | Medium | Medium | Increase identity anchor percentage to 3% of all data. Add identity injection to system prompt. |
| **Math accuracy plateau** | Medium | Medium | Accept 75%+ as V2.5 target. True math improvement may need larger base model (V3). |
| **Data generation too slow** | Low | Low | Use both llama3:70b (complex) + qwen3-coder (bulk) in parallel. |
| **New data degrades existing strengths** | Low | High | Run V2 benchmark after each training stage. Rollback if regression >5%. |
